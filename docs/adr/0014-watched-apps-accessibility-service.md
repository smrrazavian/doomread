# Watched apps are heard by an AccessibilityService that only reports the app in front, through one cached Flutter engine

Partly superseded by ADR 0015: in the Work app only, the service now looks up given view ids, to tell Shorts apart.

During a Session, opening a Watched app brings up the Urge screen. On Android, a small Kotlin edge (`Watch.kt`) holds an AccessibilityService, `WatchService`. It subscribes to `typeWindowStateChanged` only, can't read window content, and isn't an accessibility tool. It sends one thing over a hand-written method channel (`doomread/watch`): the package and label of the app that came to the front. Dart decides everything else. `UrgeWatch` asks core (`raisesUrge`, driven by `WatchRules` data: the user's picks, minus settings and package installers, which are never Watched) and appends an `urge` event to the journal. Reading shows the Urge screen while the journal has one open, and the After-a-slip screen after a Slip. So the Urge survives a restart like the rest of the Session, and #7's Shorts rules can extend the rules data without new native code.

The service is only useful if Dart is running when the Watched app opens, including after the user swipes Doomread away. So the app has one Flutter engine for the whole process, kept in `FlutterEngineCache` (`Engine` in `Watch.kt`). MainActivity takes it in `provideFlutterEngine` and never destroys it. Whichever of the Activity or the service needs the engine first starts it. Dart pushes a "watching" flag (a Session is open) that's kept in SharedPreferences, and the service starts the engine only while it's set, so app switches outside a Session cost nothing. When the service starts the engine, the first report waits in Flutter's channel buffer until Dart listens. Channels that need no Activity (`break_over`, `watch`) are set up with the engine. The notification and widget channels are still set up by the Activity, and an Activity that attaches to an engine already running hands its launch tap over as a new one. So if the process died and the service starts the engine before any Activity, the Session notification can't be updated until the user opens Doomread. The one posted before the process died stays up. If that turns out to matter, those channels can move onto the engine too, with the application context.

To show the Urge, Dart asks the edge to start MainActivity over the Watched app. Android lets an app start an activity from the background while the system has its AccessibilityService bound. After a Slip, the edge launches the app by its launch intent. The picker lists launchable apps, which a `<queries>` entry for MAIN/LAUNCHER makes visible, so we don't need `QUERY_ALL_PACKAGES`. The service can't be turned on by the app. The Watched apps screen and the first Start show a prominent disclosure that needs an affirmative tap, as Google Play asks, and then open the system's Accessibility settings.

We chose an AccessibilityService over `UsageStatsManager` polling as the primary method because it reports instantly, with no polling and no overlay permission, the way one sec does. The design names UsageStats as the fallback (#8) for Android 17's Advanced Protection. We chose one cached engine over a second headless engine with its own Dart entrypoint because the app's listeners (the journal, Settings, the notifications) already live in the one tree, and a second isolate would need its own database connection and copies of them. The cost is that the engine stays in memory for as long as the process lives, which the bound service keeps alive.

# The "break's over" notification is an AlarmManager alarm in a small Kotlin edge

When the user takes a Planned break, the app should call them back when it ends, even if they've gone off into a Watched app and the system has killed Doomread. The "break's over" notification is set in Dart from the journal alone (`BreakOverAlarm`), with its text already in the app's language. It's pushed over a hand-written method channel to one Kotlin file (`BreakAlarm.kt`), which sets one `AlarmManager` alarm for a `BroadcastReceiver` (`BreakOverReceiver`). When the alarm goes off, the receiver posts the notification with no Flutter engine running. Setting a new alarm replaces the old one (same request code and component). When the user comes back or stops, the app cancels the alarm and takes the notification away. Like ADR-0009, the app needs no foreground service, timer or wake lock, and when the app starts again the alarm is set again from the journal.

The alarm is exact (`setExactAndAllowWhileIdle`) when `canScheduleExactAlarms()` says the user allows it, or always below Android 12. Otherwise it's inexact (`setAndAllowWhileIdle`). The manifest declares `SCHEDULE_EXACT_ALARM`, not `USE_EXACT_ALARM`. `USE_EXACT_ALARM` is granted without asking, but it's limited to a few use cases under a Google Play policy, so a reading app shouldn't lean on it. On Android 14+, `SCHEDULE_EXACT_ALARM` is denied by default for new installs of apps targeting Android 13 or higher. So for most new users, the inexact branch is what runs, and the app doesn't ask for "Alarms & reminders" access.

What the Android docs (developer.android.com, "Schedule alarms" and the Android 14 behaviour change) promise for the inexact branch:

- `setAndAllowWhileIdle` never fires before the trigger time. From Android 12, the system fires it within one hour of that time, unless battery saving such as battery saver or Doze is in effect. Unlike plain `set`, it may also fire while the device is in Doze.
- `setWindow`'s window is typically clipped to at least 10 minutes for apps targeting Android 12 or higher, though the system "might accommodate smaller windows, especially if the alarm is scheduled to be triggered in the near future". Without allow-while-idle, it waits for the device to leave Doze.

We chose `setAndAllowWhileIdle` over `setWindow` for one reason: it may fire while the device dozes, and `setWindow` waits for Doze to end. A user on a Planned break may put the phone down, and the call back should still come. On documented lateness alone, `setWindow` is the tighter bound (about 10 minutes against an hour), and neither fits inside a 3 to 10 minute break. Only the exact branch does. So the inexact notification can come late, and that's the cost of not asking for exact alarms. If users report late "break's over" notifications, there are two ways forward: ask for "Alarms & reminders" access in context, the way ADR-0009 asks for notifications, or switch the inexact branch to `setWindow` and give up firing during Doze.

We chose a framework `AlarmManager` and a few lines of Kotlin over `flutter_local_notifications`' zoned scheduling, for the same reasons as ADR-0009: the plugin needs core library desugaring and adds a dependency for two calls. `AlarmManager` is part of the framework, so it holds to ADR-0002 in every flavour. ADR-0001 lists live notifications among the native edges, and this is their second half. WorkManager was ruled out because it doesn't promise a time.
